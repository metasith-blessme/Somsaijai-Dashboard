# SomSaiJai Sales Extractor — คู่มือฉบับรวม

เวอร์ชันเอกสาร: 1.0 — รวมโครงสร้างอ่านรายงานที่ผู้ใช้เสนอจาก Gemini กับกฎความถูกต้องของโปรเจกต์

## ขอบเขตและสถานะ

ใช้เมื่ออ่านภาพรายงานยอดขาย รายงานเงินสด สต๊อกวัตถุดิบ บรรจุภัณฑ์ ใบเสร็จ หรือสลิปค่าใช้จ่ายของ B1/B2/B3 เพื่อจัดทำ **ข้อมูลรอตรวจสอบ** เท่านั้น

ปฏิบัติตาม [OCR_RULES.md](OCR_RULES.md) เสมอ หากรายละเอียดขัดกัน ให้กฎความถูกต้องและการอนุมัติในไฟล์นั้นเป็นหลัก คู่มือนี้ไม่ได้ติดตั้งตัวแปลง JSON ตัวตรวจสอบอัตโนมัติ หรือตัวนำเข้าใหม่ และไม่ยกเลิกข้อห้ามใช้คำสั่งนำเข้าเดิมที่ยังไม่ปลอดภัย

**อ่านตามเอกสาร แยกค่าที่อ่านกับค่าที่คำนวณ ไม่เติมศูนย์แทนข้อมูลขาด ไม่แก้ตัวเลขเพื่อให้ยอดตรง และไม่อนุมัติตนเอง**

## 1. ก่อนเริ่มอ่าน

1. บันทึกและแสดงขอบเขตชุดภาพก่อนเริ่ม ระบุสาขา ช่วงเวลา ประเภทเอกสาร และสิ่งที่จะส่งมอบ งาน inventory/OCR แบบ read-only เริ่มได้โดยไม่ต้องขออนุมัติแยก แต่ต้องได้รับอนุมัติจากเจ้าของก่อนเขียนข้อมูลการเงินและก่อน deploy
2. ทำบัญชีภาพทุกไฟล์ด้วย `search_files` บันทึกชื่อทางเดินไฟล์และ SHA-256 ที่คำนวณด้วยเครื่องมือ ห้ามเดาหรือใช้ชื่อไฟล์แทน hash
3. เปิดภาพจริงด้วย `vision_analyze` หรือเครื่องมือที่แสดงภาพให้เห็น เริ่มจากภาพเต็ม แล้วจึงขยายจุดที่ไม่ชัด เก็บอ้างอิงภาพเต็มไว้ ห้ามอ้างว่าอ่านภาพแล้วจากผล OCR อย่างเดียว
4. ยืนยันสาขาและวันที่จากหลักฐานบนเอกสาร ชื่อโฟลเดอร์และวันอัปโหลดเป็นเพียงเบาะแส ถ้าขัดกันให้ตั้งประเด็นตรวจสอบ
5. รายงานสมัยใหม่อาจมีสามส่วนต่อวัน: (ก) ยอดขาย/เงินสด (ข) สต๊อกวัตถุดิบ (ค) สต๊อกบรรจุภัณฑ์/วัสดุสิ้นเปลือง แต่ห้ามสมมติว่าทุกวันหรือทุกสาขามีครบสามหน้า โดยเฉพาะข้อมูลย้อนหลังและ POS-only
6. เชื่อมหน้าด้วยสาขา วันที่ กะ และชนิดรายงาน เก็บสถานะหน้าที่ขาด หน้าที่ซ้ำ และหน้าที่อ่านไม่ได้ อย่ารวมภาพวันเดียวกันอัตโนมัติ เพราะอาจเป็นคนละกะหรือฉบับแก้ไข

## 2. อ่านรายงานยอดขายทีละส่วน

- หัวกระดาษ: วันที่ สาขา ชื่อพนักงาน กะ เวลา และหมายเหตุ การอ่านไม่ออกไม่ใช่เหตุให้ใช้วันที่จากโฟลเดอร์แทน
- แต่ละเมนู: ชื่อที่เขียนจริง เมนูมาตรฐานที่เสนอจับคู่ ขนาด/รูปแบบ หน่วย ราคา จำนวนเงินสด จำนวนสแกน จำนวนช่องทางอื่น จำนวนรวม และยอดเงินที่เขียนไว้
- รายการเขียนเพิ่ม: เก็บทุกแถว รวมถึงข้าวเหนียวมะม่วง Durain เมนู No Ice เมนูพิเศษ และรายการที่ยังไม่มีรหัสในระบบ ห้ามบังคับใส่เมนูใกล้เคียงหรือทิ้งรายการ
- สรุปการเงิน: ยอดขายตามนิยามบนฟอร์ม เงินสด สแกน ช่องทางอื่น ส่วนลด เงินคืน ค่าธรรมเนียม/รายการปรับปรุง ค่าใช้จ่าย เงินสดยกมา เงินสดนำเข้า/นำออก และเงินสดนับจริงหรือส่งมอบ
- เก็บแถวค่าใช้จ่ายแต่ละรายการพร้อมวิธีจ่ายและหลักฐานอ้างอิง แยกค่าใช้จ่ายเงินสดออกจากค่าใช้จ่ายทั้งหมด
- แยกขวด แก้ว จาน และชุด จำนวนอาหารไม่ใช่จำนวนแก้วเสมอไป เก็บยอดขายขวดที่อ่านได้โดยตรง ไม่เดาราคาจากจำนวนขวด
- `or_100` ในระบบปัจจุบันเป็นส่วนหนึ่งของ `or` ไม่ใช่จำนวนบวกเพิ่ม ถ้ากระดาษแยกแถวส้มปกติกับส้มพรีเมียม ให้เก็บทั้งสองแถวตรงตามต้นฉบับก่อน แล้วแปลงตามความหมายนี้เมื่อได้รับอนุมัติ
- เก็บ Young Coco และส่วนประกอบมะพร้าว/นมที่มีอยู่จริงในเอกสาร ไม่จำกัดข้อมูลให้เหลือเฉพาะช่องในตัวอย่าง Gemini

## 3. อ่านสต๊อกวัตถุดิบและบรรจุภัณฑ์

เก็บเป็นรายแถว: สถานที่ วันเวลานับ ชื่อสินค้า ขนาด/รูปแบบ หน่วย ยกมา รับเข้า โอนเข้า ใช้ ของเสีย โอนออก คืนสินค้า/ปรับปรุง และคงเหลือที่นับจริง

- เก็บหน่วยตามกระดาษ เช่น ตะกร้า กก. ลูก ลิตร ขวด ถุง แพ็ก ชิ้น แถว และขนาดแก้ว/ฝา ห้ามตีความว่า 1 แถวมีจำนวนชิ้นเท่าไรโดยไม่มีหลักฐาน
- เศษส่วนที่อ่านได้ชัดเจนให้ใช้เครื่องมือแปลงเป็นทศนิยม เก็บข้อความเศษส่วนต้นฉบับและวิธีแปลงด้วย
- ห้ามแปลงน้ำหนักข้าวเหนียวดิบเป็นน้ำหนักสุก หรือเทียบกิโลกรัมกับลิตรโดยไม่มีอัตราที่อนุมัติ
- การโอนของระหว่างสาขาไม่ใช่การซื้อจากภายนอกอีกครั้ง จับคู่ต้นทางและปลายทางโดยไม่ลงต้นทุนซ้ำ
- แยกการใช้ที่พนักงานบันทึก การใช้ที่คำนวณจากสมการสต๊อก และการใช้ที่ประมาณจากสูตร/ยอดขาย อย่าเปลี่ยนค่า derived หรือ estimated เป็น observed

## 4. อ่านสลิปและใบเสร็จ

อ่านสถานะชำระเงิน ยอดเงิน ค่าธรรมเนียม วันเวลา เลขอ้างอิง ผู้จ่าย/ผู้รับแบบปกปิดข้อมูลที่ไม่จำเป็น และ **บันทึกช่วยจำทุกบรรทัด** แยกวันที่จ่ายออกจากช่วงบริการหรือวันที่รับสินค้า

- เก็บข้อความหมายเหตุเดิมก่อนจัดหมวด เช่น `ฝา8แถว` ต้องคงข้อความนี้ไว้แม้เสนอหมวด Packaging
- อ่านรายการย่อย จำนวน หน่วย ราคาต่อหน่วย ยอดย่อย ค่าส่ง ภาษี ส่วนลด และยอดรวมตามที่มีหลักฐาน
- หมวด COGS เพิ่มเติมที่เจ้าของอนุมัติคือ `Durain` (ทุเรียน) และ `Sticky Rice` (ข้าวเหนียว) เก็บตัวสะกดของหมวดตามนี้ แต่เก็บชื่อที่เขียนจริงใน raw text แยกกัน
- สลิปหลายสินค้าให้แยกตามยอดย่อยที่มีหลักฐานเท่านั้น ชื่ออาหารรวม เช่น ข้าวเหนียวทุเรียน ไม่ได้พิสูจน์ว่าจ่ายค่าวัตถุดิบแต่ละอย่างเท่าไร
- ใบแจ้งหนี้ ใบเสร็จ และสลิปจ่ายอาจเป็นหลักฐานของรายการเดียวกัน ตรวจเลขอ้างอิง เวลา คู่ค้า และรายการเดิมข้ามทุกสาขาก่อนเสนอเพิ่ม
- เงินแบ่งกำไร เงินเติมทุน เงินโอนระหว่างบัญชี เงินมัดจำ และการซื้อสินทรัพย์ต้องแยกจากค่าใช้จ่ายดำเนินงานตามกฎหลัก ห้ามใช้ชื่อผู้รับหรือคำแรกในหมายเหตุเป็นตัวตัดสินอย่างเดียว
- ภาพสลิปไม่ใช่การรับรองธุรกรรมจากธนาคาร หากยังไม่ได้ตรวจสอบกับหลักฐานธนาคาร ให้ระบุขอบเขตหลักฐานตามจริง

## 5. ตรวจสมการโดยไม่แก้ค่าต้นฉบับ

ใช้ `execute_code` หรือ `terminal` คำนวณ ไม่คำนวณจากความจำ เก็บ observed, expected, difference และสถานะของแต่ละการตรวจ เงินใช้จำนวนเต็มหน่วยสตางค์สำหรับการเปรียบเทียบ

| การตรวจ | เงื่อนไขและความหมาย |
|---|---|
| จำนวนขายต่อแถว | เปรียบเทียบยอดรวมที่เขียนกับผลรวมจำนวนทุกช่องทางที่เกี่ยวข้อง ตรวจว่าจำนวนเป็นคนละกลุ่ม ไม่ซ้ำกัน |
| ยอดขายต่อแถว | จำนวน × ราคาที่ใช้จริง โดยแยกส่วนลด/เงินคืน/การปรับปรุงที่มีหลักฐาน เก็บยอดที่เขียนกับยอดคำนวณคนละช่อง |
| ยอดขายทั้งวัน | รวมแถวสินค้าทั้งหมด รวมเมนูเพิ่มและขวด โดยให้ฐานยอดก่อน/หลังส่วนลดตรงกับยอดสรุป |
| ช่องทางชำระเงิน | รวมเงินสด สแกน และช่องทางอื่นตามนิยามเอกสาร ไม่ตั้ง scan = revenue - cash เพื่ออ้างว่าอ่านได้ |
| ยอดขายหักค่าใช้จ่ายที่รายงาน | แสดงเป็นค่าคำนวณแยก ไม่เรียกกำไรสุทธิหรือ net sales ทางบัญชี เก็บชื่อช่องเดิมจากกระดาษไว้ต่างหาก |
| เงินสดที่ควรเหลือ | ยกมา + ขายเงินสด + เงินสดนำเข้า - ค่าใช้จ่ายเงินสด - เงินสดนำออก รวมคืนเงินสดแยกเฉพาะเมื่อยังไม่หักในยอดขาย ห้ามนับซ้ำ เปรียบเทียบกับยอดนับจริง ณ เวลาเดียวกัน |
| สต๊อก | ยกมา + รับเข้า + โอนเข้า - ใช้ - ของเสีย - โอนออก และรายการคืน/ปรับปรุงที่มีหลักฐาน เทียบกับคงเหลือที่นับจริงในหน่วยเดียวกัน |
| สลิปที่แบ่งรายการ | ผลรวมยอดย่อยและองค์ประกอบภาษี/ส่ง/ส่วนลดต้องเท่ากับยอดแม่ ห้ามลงยอดแม่และยอดลูกเป็นค่าใช้จ่ายซ้ำ |

สถานะการตรวจมี `pass`, `fail`, `not_testable` หากข้อมูลจำเป็นขาด ให้ใช้ `not_testable` ไม่ใช่ pass ผลต่างที่ไม่เป็นศูนย์ต้องคงอยู่และส่งตรวจ แม้เจ้าของอนุมัติข้อยกเว้นแล้วก็ไม่เปลี่ยนผล fail ให้เป็น pass เทียม

ราคาตรวจเชิงทฤษฎีต้องตรงสาขาและช่วงวันที่จาก `business_rules.js` หรือหลักฐานราคาที่เจ้าของยืนยัน ถ้าราคาในกระดาษขัดกับระบบ ให้เก็บทั้งสองและส่งตรวจ ห้ามแก้ยอดขายให้เข้ากับราคาเดิมของระบบ

## 6. ค่าที่ไม่ชัดเจนและการอ่านรอบสอง

- ใช้สถานะ field: `observed`, `missing`, `illegible`, `ambiguous`, `not_applicable`, `derived`, `estimated`
- ค่าที่ขาด อ่านไม่ออก กำกวม หรือไม่เกี่ยวข้องใช้ `null` พร้อมสถานะ ไม่ใช้ 0; จำนวนศูนย์ที่เขียนชัดเจนจึงเป็น observed 0
- ตัวเลขขีดฆ่า: เก็บข้อความเดิมกับตัวเลือกที่เห็น เลือกเลขแก้ไขได้เมื่อชัดเจนเท่านั้น ถ้าไม่ชัดให้ส่งตรวจ ไม่เลือกเพราะทำให้สต๊อกลงตัว
- แปลงวันที่เป็น `DD/MM/YYYY` หลังยืนยันปฏิทิน พ.ศ./ค.ศ. และความถูกต้องของวันจริงเท่านั้น เก็บข้อความวันที่เดิมไว้ ห้ามบังคับปีให้เป็น 2026
- อ่านรอบสองจากภาพจริงโดยไม่ดูคำตอบรอบแรกก่อนเปรียบเทียบ โดยเฉพาะวันที่ สาขา ยอดเงิน จำนวนสินค้า หน่วย และยอดแยกสลิป ความเห็นตรงกันของสองโมเดลยังไม่ใช่ human approval
- POS-only อนุญาตให้มีรายได้ที่อ่านได้ แต่จำนวนแก้ว สัดส่วนเมนู ช่องทางชำระ และสต๊อกที่ไม่มีหลักฐานต้องยังเป็น unknown หรือ estimated แยกส่วน ห้ามสร้างให้ครบฟอร์ม

## 7. สัญญาข้อมูล JSON สำหรับรอตรวจสอบ

นี่คือ **รูปแบบเอกสารเสนอใช้สำหรับ review** ไม่ใช่ JSON Schema ที่บังคับตรวจด้วยโปรแกรม และไม่ใช่รูปแบบนำเข้าของสคริปต์เดิม

### โครงสร้างหลัก

- `schema_version`: `somsaijai-extraction-review-v1`
- `batch_id`: รหัสชุดงานที่กำหนดจริง
- `sources[]`: ทุกภาพพร้อม source_id, path, sha256, document_type, page, disposition; ห้ามเก็บบัญชีธนาคารเต็มหรือ QR ในผลที่เผยแพร่สาธารณะ
- `records[]`: แต่ละสาขา/วัน/กะมี record_id, branch, date, staff, shift_hours, source_ids, missing_pages และสถานะ `ready_for_review` หรือ `needs_review`
- `financials`: ช่องรายได้และเงินสดที่อ่านได้ รวมรายการช่องทางอื่น ส่วนลด เงินคืน และรายการปรับปรุง ไม่ยุบความหมายก่อนตรวจ
- `sales_items[]`: ทุกแถวเมนู โดยมี name_raw, proposed_code, variant, unit, unit_price, cash_qty, scan_qty, other_channel_qty, reported_total_qty, reported_sales; proposed_code เป็น null ได้เมื่อยังไม่มี mapping
- `stock_items[]`: ทุกแถวสต๊อกพร้อม location, count_time, item_name_raw, variant, unit, opening, received, transfers_in, used, waste, transfers_out, adjustments, reported_closing
- `expense_documents[]`: slip/invoice/receipt พร้อม payment_date, service_period, payment_status, payment_direction, payment_amount, currency, fee, reference, sender, bank_recipient, economic_beneficiary, account_relationship_evidence, purpose_raw, purpose_proposal, paying_party, paying_branch, benefiting_branches, `memo_lines[]` แบบเรียงลำดับพร้อม source location, handwritten_annotations, items, payment_allocations และ duplicate_candidates; identity/account fields ต้องปกปิดเลขที่ไม่จำเป็น ทุก item เก็บ item_raw, category_proposal, quantity, unit, unit_price, line_amount, source location และ parent reference. `memo_raw` อาจเก็บเพิ่มเพื่อคงข้อความรวม แต่ห้ามใช้แทน `memo_lines[]`
- `computed`: ผลคำนวณพร้อม formula, input_paths, value, unit; input ไม่ครบให้ value เป็น null และไม่อ้างว่าเป็น observed
- `checks[]`: rule, input_paths, observed, expected, difference, unit, status, reason; สมการที่ขาดข้อมูลต้องบอกช่องที่ขาด
- `issues[]`: record/field อ้างอิง ประเด็น หลักฐาน และคำถามที่ต้องให้คนตัดสิน
- `review`: reviewer, reviewed_at, approval_reference เป็น null จนกว่าจะมีการตรวจและอนุมัติจริง `import_allowed` ต้องเป็น false ในผลจาก extractor เสมอ

### ข้อมูลรายช่อง

ทุกค่าที่ถอดจากภาพ รวมถึงวันที่ สาขา ข้อความ ตัวเลข และหน่วย ให้เก็บเป็น field object เพื่อไม่ทำหลักฐานหาย ค่าข้อความใช้ string; ค่าจำนวนใช้ number; ค่าเงินที่ normalize แล้วใช้ integer satang และ unit เป็น `satang` เก็บหน่วยต้นฉบับใน raw text หรือช่อง unit ของรายการด้วย

ตัวอย่างต่อไปนี้เป็น **โครงสร้างสำหรับช่องยอดเงินที่อ่านไม่ออก ไม่ใช่ธุรกรรมจริง**:

```json
{
  "raw_text": null,
  "value": null,
  "state": "illegible",
  "unit": "satang",
  "source_id": null,
  "location": null,
  "alternatives": [],
  "reason": "ต้องระบุจุดที่อ่านไม่ออกและแนบ source_id จริงก่อนส่งผล"
}
```

`source_id` และ `location` ของช่องที่มีอยู่ในภาพต้องชี้ไปยังภาพและตำแหน่งจริงก่อนส่งผล; null ในตัวอย่างเป็น placeholder เท่านั้น ไม่อนุญาตให้ปลอม ID, hash หรือข้อความที่ไม่ได้อ่าน สำหรับ missing page ให้เชื่อม issue กับชุดรายงานและ missing_pages แทนการอ้างตำแหน่งภาพที่ไม่มี

เก็บรายการว่างเป็น `[]` แต่ต้องระบุว่าไม่มีรายการจริงหรือเอกสารยังขาดใน issues/completeness; อย่าใช้ array ว่างเป็นหลักฐานว่าค่าใช้จ่ายเป็นศูนย์

## 8. ความเข้ากันได้กับ Excel และ Dashboard

ตัวนำเข้าเดิมรับวันที่ `DD/MM/YYYY` และช่องแบน เช่น `rev`, `cash`, `scan`, `exp`, `or`, `or_100`, `yco`, `uo` ไม่รับ object ของหลักฐานหรือโครงสร้างซ้อนด้านบน

จึงต้องมีตัวแปลงที่ผ่านการทดสอบและอนุมัติก่อนใช้งานจริง ตัวแปลงต้อง:

1. แปลงยอดเงินจากสตางค์เป็นบาทอย่างชัดเจนและไม่เปลี่ยนความหมายของยอด
2. แปลงชื่อเมนู/หน่วย/จำนวนส้มรวมและพรีเมียมอย่างมีหลักฐาน ไม่เพิ่มจำนวนซ้ำ
3. คงข้อมูล Young Coco ขวด เมนูเพิ่ม และรายละเอียดสต๊อก/สลิปไว้ ไม่ลบทิ้งเพื่อให้เข้ากับ schema เก่า
4. ปฏิเสธการนำเข้าหากมีข้อมูลสำคัญที่ปลายทางยังไม่รองรับหรือยังไม่อนุมัติ ห้ามยัด unknown เป็นศูนย์
5. เก็บหลักฐาน review แยกจากไฟล์เผยแพร่สาธารณะ และส่งต่อเฉพาะฟิลด์ที่อนุมัติให้เผยแพร่

อย่าเขียนผล extractor ลง `pending_verification.json` ที่ใช้นำเข้าจริงโดยตรง ให้สร้าง review artifact แยกตาม batch ภายในพื้นที่ที่ไม่เผยแพร่ และห้ามเรียก pipeline หรือ deploy จากงาน OCR

## 9. สิ่งที่ต้องส่งมอบและเกณฑ์เสร็จงาน

- รายการภาพทั้งหมดและ disposition ที่นับด้วยเครื่องมือ พร้อมหน้าขาด/วันขาด/ภาพซ้ำ
- JSON review ที่ parse ได้จริง ไม่มี NaN/Infinity ไม่มีค่าที่เดา และทุก field มีหลักฐานหรือเหตุผลของ unknown
- ตารางตรวจยอดขาย สต๊อก และสลิปตาม OCR_RULES.md พร้อมผลต่างและรายการคำถาม
- การอ่านรอบสองและการตรวจสำคัญทุกข้อเป็น pass/fail/not_testable อย่างซื่อตรง
- การอนุมัติต้องมาจากคน ระบุผู้ตรวจ วันเวลา ขอบเขตและค่าที่อนุมัติ การเปลี่ยนภาพหรือค่าข้อมูลทำให้ approval เดิมใช้ไม่ได้
- ก่อนนำเข้าจริงต้องมี safe importer ที่ทดสอบแล้ว สำรอง dry run อ่านกลับ และพิสูจน์ว่ารันซ้ำไม่เพิ่มรายการ ตามกฎหลัก

**การจัดทำ JSON สำเร็จ ≠ ตรวจภาพถูกทุกช่อง ≠ หลักฐานชำระเงินแท้ ≠ อนุมัติให้นำเข้า ≠ ข้อมูลการเงินครบถ้วน**
